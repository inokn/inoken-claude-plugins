# 判定の基準と、たくさんのサイトを進める順番

## 判定（report.py が付ける）

| 判定 | 意味 | 典型例 |
|---|---|---|
| **A** そのままで可 | PHP を切り替えるだけでよい | 同じ系列内のパッチ更新（8.2.32 → 8.2.35）。点検で問題なし |
| **B** 更新で対応 | WordPress 本体・プラグイン・テーマを更新すれば済む | 自作コードにエラーが無く、既製品が古いだけ |
| **C** コードの修正が必要 | 自作コード（またはディレクトリ外の部品）に、移行先で動かない書き方がある | mysql_* / each() / create_function など |
| **D** 作り直しを検討 | 自作コードの要修正が 200 箇所以上 | 古い独自 CMS、PHP 5 時代の大きなシステム |

- **D は「人が判断する」印**。直せないという意味ではない。直す手間と、作り直し・サイトの閉鎖を比べる材料にする
- 警告（非推奨）は判定に入れていない。今は動くが、次に上げるときにエラーになる。余裕があれば一緒に直す
- 点検で分かるのは「書き方」だけ。A でも、実行時の落とし穴（`php-changes.md` の3章）が残っていることがある

## 移行先（targets.json）

脆弱性の修正が入った版のうち、今の版から一番近いもの。最低ラインは 8.2。

| 今の版 | 移行先 | 点検 |
|---|---|---|
| 7.x / 8.0 / 8.1 | 8.2 の修正版 | する（系列をまたぐ） |
| 8.2.x | 8.2 の修正版 | しない（パッチ更新のみ） |
| 8.3.x / 8.4.x / 8.5.x | 同じ系列の修正版 | しない |

**8.2 はセキュリティ修正が 2026-12-31 で終わる。** 8.2 への移行は応急処置なので、レポートと作業票に必ず書く。
次の修正版が出たら `targets.json` の `targets` を書き換える（スクリプトは直さなくてよい）。

## たくさんのサイトを進める順番

棚卸し表の列（顧客情報の有無、保守契約の有無、今の PHP 版）を使って並べる。

1. **今の PHP が 8.1 以下**で、**個人情報を扱う**（フォーム・会員・EC）サイト — 修正版が出ない版で、漏れたときの被害が大きい
2. 今の PHP が 8.1 以下のその他のサイト
3. 8.2 以上のサイト（パッチ更新のみ。まとめて短時間で終わる）

同じ系列のサイトは、サーバー側でまとめて切り替えられることが多い。判定 A のサイトを先に片付けると、件数が早く減る。
保守契約のないサイトは、作業の前にお客様への連絡・費用の相談が要る（スキルは関与しない）。
