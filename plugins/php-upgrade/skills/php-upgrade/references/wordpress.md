# WordPress サイトの扱い方

## 部品ごとの方針

| 部品 | 点検するか | やること |
|---|---|---|
| WordPress 本体（wp-admin / wp-includes / ルートの wp-*.php） | しない | 管理画面から最新へ更新。**本体のファイルは絶対に手で直さない**（次の更新で消える） |
| WordPress.org 配布のプラグイン・テーマで更新があるもの | しない | 最新版へ更新。手で直さない |
| WordPress.org 配布で最新だが、2年以上更新が無いもの | 参考に点検 | 開発が止まっている可能性。エラーがあれば代わりのプラグインを探す |
| WordPress.org で配布停止（closed）のもの | する | セキュリティ上の理由で止まったものもある。置き換えを強く勧める |
| ディレクトリ外（`external`） | する | 有料プラグイン・有料テーマ・制作会社の自作のどれか。**人に出どころを聞いてから**扱いを決める（下） |
| 自作（`custom`）、mu-plugins、ドロップイン（wp-content 直下の PHP） | する | 修正してよい |
| 子テーマ | する（ディレクトリ外なら） | 子テーマはサイトごとの自作がほとんど。修正してよい |

## ディレクトリ外の部品の見分け方

`inventory.json` の `author` / `update_uri` と、フォルダの中身から推測し、**最後は人に確認する**。

- **有料（市販）**: `Update URI` が販売元のURL、ライセンスキーの入力画面がある、`vendor` フォルダや自動更新の仕組み（`plugin-update-checker` など）を持っている、名前で検索すると販売ページがある（例: Advanced Custom Fields PRO、Elementor Pro、有料テーマの TCD・SANGO など）
  → **手で直さない**。販売元の最新版に更新する（アカウントやライセンスが要るので人の作業）。販売終了なら置き換えを検討
- **自作（制作会社が作った）**: 作者が制作会社名、ファイル数が少ない、このサイト専用の名前
  → 修正してよい
- 名前が WordPress.org のものと同じフォルダなのに中身が違う（`note` に「名前が違う」）ものは、自作として扱う。**WordPress の自動更新で別物に上書きされる危険がある**ので、レポートで人に知らせる

## 作業の順番（検証環境で）

1. バックアップ（ファイルと DB）
2. **PHP はまだ上げずに**、WordPress 本体 → プラグイン → テーマの順に最新へ更新し、表示を確認
3. 修正したファイルをアップロード
4. PHP を移行先へ切り替えて、表示・フォーム・管理画面を確認
5. 問題が無ければ、本番で同じ順に行う

本体やプラグインを先に上げるのは、古い PHP のまま上げられるうちに上げるため（最新版は古い PHP に対応していないことがある。逆順だと管理画面に入れなくなることがある）。
ただし最新版が今の PHP に対応していない場合（`requires_php` が今の版より新しい）は、PHP を上げるまで「今の PHP で入る最新版」に留める。

## 使っていないプラグイン・テーマ

DB を見ないと有効かどうか分からないため、点検では区別していない。無効のまま置いてあるプラグイン・テーマも攻撃の入口になるので、**使っていないものは削除する**よう作業票に書き添えるとよい（削除は人が管理画面で行う）。

## PHP と WordPress の対応

対応表: https://make.wordpress.org/core/handbook/references/php-compatibility-and-wordpress-versions/

| PHP | 必要な WordPress |
|---|---|
| 8.2 | 6.1 以上 |
| 8.3 | 6.4 以上 |
| 8.4 | 6.7 以上 |
| 8.5 | 6.9 以上 |

（`targets.json` の `wordpress_min_for_php` と同じ。表が変わったら両方を直す）

## このスキルがやらないこと

- wp-config.php を開く・書き換える（`WP_DEBUG` を有効にしたいときは人が検証環境で行う）
- 管理画面での更新、プラグインの削除、DB の操作
- uploads の中のファイルの実行・削除（PHP が見つかったら報告するだけ）
